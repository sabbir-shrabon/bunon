**1\. Master Security Decisions & Why Each Rule Exists**

Below are the six core security pillars you locked in, why each is required for Bunon, and how the Admin Console controls the live thresholds.

| Security Pillar | Why It Matters & Decided Implementation in Bunon |
| :---- | :---- |
| **1\. Strict PostgreSQL Row-Level Security (RLS) & Zero Client Access to System Tables** | **• Why it matters:** Supabase exposes a public 'anon' key in the browser for authentication. If a table lacks RLS, an attacker can use the browser console to read or modify other users' rows or read your internal AI prompts. **• Decided Rule:** Enable RLS on all 22 tables. All 10 System/Admin tables ('prompt\_versions', 'goal\_categories', 'regional\_knowledge', 'ai\_calls', 'payments', 'payment\_events', 'refund\_requests', 'system\_settings', 'pricing\_plans', 'admin\_audit\_log') have ZERO client policies—only your Next.js server-side API routes (using the server-only DB connection) can touch them. All 12 User tables (including 'push\_subscriptions') enforce 'auth.uid() \= user\_id' so a user can never query another user's private goals, tasks, proofs, or day notes. |
| **2\. Private Storage Bucket & Short-Lived Signed URLs** | **• Why it matters:** User proofs include personal photos, 15–30s videos, and PDFs. If stored in a public bucket, anyone who guesses or scrapes a URL could view private user files forever. **• Decided Rule:** Store all proof files in a single PRIVATE Supabase Storage bucket ('bunon-proofs'). Uploads use a 60-second Single-Use Signed Upload URL generated by '/api/tasks/:id/evidence' only after checking the user's daily photo limit and storage quota. Viewing private proofs on Today/Timeline uses 1-hour Signed View URLs generated only for the authenticated owner. |
| **3\. The 4-Gate AI Token Firewall (Dynamic Caps in Admin Screen 142\)** | **• Why it matters:** Every Gemini API call costs real USD. A bot, loop bug, or malicious user pasting 50,000 words could drain your monthly Gemini budget in minutes. **• Decided Rule: Every AI endpoint passes through 4 server-side gates before calling Gemini: (Gate 1\) Input length cap (max 500 chars/answer) \+ server-only API key; (Gate 2\) Dynamic Spend Circuit Breakers \+ Graceful Model Downgrade stored in 'system\_settings' (defaults: \$5.00/day Global Cap, \$0.15/mo Free User Cap, \$0.80/mo Pro User Cap — core pipelines 1, 2, 3, 5, 6, 7 always run, downgrading automatically from Pro/Flash to Flash-Lite if spend nears the cap before tripping the emergency kill switch); (Gate 3\) Zero-token Day Note saves (Day Notes save at \$0 tokens and are digested on weekly rollover or explicit Stuck/re-plan; max 1 Pipeline 4 call/goal/day); (Gate 4\) Sliding-window rate limit (max 5 AI calls/min per user/IP \-\> triggers Screen 120 'Wait 30s').** |
| **4\. Hardened Admin Console Security (admin.bunon.app)** | **• Why it matters:** The Admin Console controls live AI prompts, pricing, user suspensions, and payment approvals. Compromising an admin account would compromise the entire app. **• Decided Rule:** (a) Subdomain isolation in 'middleware.ts' ('bunon.app/admin' returns 404); (b) Separate 'HttpOnly, Secure, SameSite=Strict' admin session cookie ('\_\_Host-bunon\_admin\_session') that expires after 4 hours of inactivity; (c) Mandatory TOTP 2FA (Google Authenticator / 2FAS) verified cryptographically on the server on EVERY '/api/admin/\*' request; (d) 5-attempt brute-force lockout (15-minute cooldown \+ automatic alert in 'admin\_audit\_log'); (e) SQL-level privacy projection so admins see counts/metadata only and can never query private user proofs or day notes. |
| **5\. Payment Webhook & Fake SMS Anti-Spoofing (UddoktaPay / bKash)** | **• Why it matters:** In Stage 1 (UddoktaPay) and Stage 2 (SSLCommerz / bKash), attackers may try faking browser redirect parameters, spoofing webhook payloads, or replaying a used bKash Transaction ID. **• Decided Rule:** Browser redirects never unlock Pro. The server verifies the HMAC webhook signature, calls the gateway's server-to-server 'verifyPayment()' API to confirm the exact BDT amount matches 'pricing\_plans', and inserts/updates inside a 'SELECT ... FOR UPDATE' transaction with a PostgreSQL 'UNIQUE' constraint on 'gateway\_transaction\_id'. |
| **6\. Dynamic Storage Quotas & Media Limits (Controlled in Admin Screen 142\)** | **• Why it matters:** Cloud storage costs scale with video and photo uploads. You need clear defaults now and instant admin control later as revenue grows. **• Decided Rule:** Default limits are 50 MB total per Free user (\~200+ compressed photos), 2 GB (2,048 MB) total per Pro user, 10 MB max per single file/video/PDF, and 30 seconds max per Pro video. All four numbers live in 'system\_settings' and can be adjusted live by SUPER\_ADMIN in Admin Screen 142 (via Confirm Modal 144). |

**2\. The 4-Gate AI Token Firewall (Zero Unauthorized Token Spend)**

Every time a user triggers one of the 7 AI pipelines (Onboarding Follow-ups, Roadmap Generator, Weekly Planner, Daily Adjuster, Weekly Review, Re-plan, or Next-Goal Bridge), the request MUST pass through all four server-side gates inside '/lib/ai/firewall.ts' before a single token is sent to Google Gemini.

| AI Firewall Gate | What It Blocks & Exact Server-Side Enforcement |
| :---- | :---- |
| **Gate 1: Authentication, Input Sanitization & Character Caps** | **• Blocks:** Unauthenticated callers, prompt-stuffing (pasting huge text to burn input tokens), and prompt-injection attempts. **• Enforcement:** Requires a valid, non-suspended Supabase session ('users.status \= ACTIVE'). Hard-truncates and validates input lengths before building the prompt: Goal Title \<= 150 chars, Goal Why \<= 350 chars, Onboarding Answers \<= 500 chars each, Day Note \<= 500 chars. Wraps all user-supplied strings inside explicit XML delimiters ('\<user\_input\>...\</user\_input\>') and instructs Gemini in 'CORE\_SYSTEM\_IDENTITY' to treat anything inside '\<user\_input\>' strictly as data, never as system instructions. |
| **Gate 2: Sliding-Window Rate Limiter (Per User ID & Per IP)** | **• Blocks:** Rapid button clicking, automated scripts, and DDoS bursts. **• Enforcement:** Enforces a strict sliding window (configurable in 'system\_settings'):   \- Max 5 AI requests per minute per User ID (and max 10 per minute per IP).   \- If exceeded, returns HTTP 429 ('RATE\_LIMITED') with 'retry\_after\_seconds: 30', which triggers Bottom Sheet 120 ('Please wait a moment before trying again — Wait 30s') without calling Gemini. |
| **Gate 3: Feature Allowance & Idempotency Check** | • Blocks: Users repeatedly regenerating roadmaps or burning tokens on every Day Note save. **• Enforcement: Queries PostgreSQL before calling Gemini:**   \- Initial Roadmap & 'This Doesn't Fit Me' Regeneration (Pipeline 2): Free users get 1 initial roadmap \+ 1 free 'This doesn't fit me' regeneration on Screen 17 per goal (Pro gets up to 3 regenerations, controlled in 'system\_settings.free\_roadmap\_allowance'). The first roadmap is preserved in 'goals.previous\_roadmap\_json' so the user can toggle between Plan A and Plan B before locking. Retry after an AI error (State 21\) does not deduct allowance.   \- Zero-Token Day Note Save & Daily Adjuster (Pipeline 4): Saving a Day Note (Sheet 34\) NEVER calls Gemini immediately—it runs a 0ms server-side crisis regex check, saves to 'day\_notes' at \$0 token cost ('digested\_in\_plan \= false'), and is digested when the week finishes (Pipeline 5/3) or when the user explicitly taps 'Stuck?' / Re-plan. Explicit Pipeline 4 calls ('Stuck?' on Sheet 37b or 'Not useful' on Sheet 22b) are capped at 1 per goal per logical day. A second same-day 'Too tired / No time' tap switches inline to 'min\_version\_10m' (\$0 tokens); a second 'Not useful' tap marks 'marked\_not\_useful \= true' and unlocks the next deliverable immediately (\$0 tokens; manual task editing Sheet 22c is removed).   \- Manual Full Restructure (Pipeline 6 from Sheet 52): Free \= 1 per goal ('goals.restructure\_count \< 1'); Pro \= 4 per goal per month. (Switching 'plan\_style' between 'FLEXIBLE\_WEEK' and 'DAILY\_ADAPTIVE' in Sheet 52 runs in 100% TypeScript code at \$0 tokens and never deducts restructure allowance). |
| **Gate 4: Dynamic USD Spend Circuit Breakers & Auto Kill Switch** | • Blocks: Runaway wallet drain from unexpected traffic spikes while ensuring active users are never stranded by a silent companion. **• Enforcement: Reads live caps from cached 'system\_settings' (editable in Admin Screen 142):**   1\. Graceful Model Degradation ('graceful\_model\_fallback\_enabled \= true'): Always fund core journey pipelines (Pipelines 1, 2, 3, 5, 6, 7, Welcome Back, and Rescue). If daily spend reaches 80% of 'global\_daily\_ai\_cap\_usd' (or a user reaches their monthly cap), the AI Service Layer automatically downgrades high-tier pipelines from 'gemini-2.5-pro'/'gemini-2.5-flash' to 'gemini-2.5-flash-lite' instead of blocking the user.   2\. Emergency Global AI Kill Switch ('ai\_kill\_switch'): Only trips if 24h spend exceeds 100% of 'global\_daily\_ai\_cap\_usd' (default '\$5.00/day') and graceful fallback is disabled, returning calm State 118 while keeping Today tasks, sub-step checks, proof uploads, and Timeline 100% functional.   3\. Per-User Monthly Spend Dials (defaults: '\$0.15/mo' Free in 'free\_monthly\_ai\_cap\_usd', '\$0.80/mo' Pro in 'pro\_monthly\_ai\_cap\_usd'): Rations only optional daily adjustments, extra roadmap regenerations, and manual restructures once reached. |

**3\. Admin Console Security, 2FA & Privacy Architecture (admin.bunon.app)**

Because the Unified Next.js codebase serves both 'bunon.app' and 'admin.bunon.app', security is enforced at three independent layers: Edge Middleware, Server API Guards, and Database Projections.

| Admin Security Layer | Technical Implementation |
| :---- | :---- |
| **Layer 1: Subdomain Isolation & Security Headers (middleware.ts)** | **• Hostname Routing:** Next.js 'middleware.ts' inspects the 'Host' header on every request:   \- Requests to 'bunon.app/admin\*' or 'bunon.app/api/admin\*' immediately return HTTP 404 so admin routes appear non-existent on the public user domain.   \- Requests to 'admin.bunon.app' rewrite internally to '/app/(admin)/\*' and attach strict headers: 'Content-Security-Policy', 'X-Frame-Options: DENY' (blocks clickjacking), 'Strict-Transport-Security', and 'Referrer-Policy: no-referrer'. |
| **Layer 2: 4-Hour Isolated Cookie & Mandatory Server-Side TOTP 2FA** | **• Separate Cookie Scope:** Admin sign-in issues an encrypted session token in '\_\_Host-bunon\_admin\_session' ('HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=14400' — 4 hours). Logging into the user app on 'bunon.app' never grants a session on 'admin.bunon.app'. **• Two-Stage Token ('totp\_verified'):** Step 1 (Email \+ Password on Screen 123\) issues a temporary 5-minute pre-2FA token ('totp\_verified: false') that can ONLY call '/api/admin/auth/totp-setup' (124) or '/api/admin/auth/totp-verify' (125). Step 2 (entering a valid 6-digit RFC 6238 code from Google Authenticator / 2FAS) upgrades the session to 'totp\_verified: true'. • Universal Admin API Guard ('requireAdmin(role)'): Every '/api/admin/\*' route runs a single wrapper that verifies: (1) valid '\_\_Host-bunon\_admin\_session', (2) 'totp\_verified \=== true', (3) live DB check that 'users.role IN (ADMIN, SUPER\_ADMIN)' and 'users.status \=== ACTIVE', and (4) for Super-Admin-only routes (Prompts, Categories, Refunds, Admins, Settings), enforces 'users.role \=== SUPER\_ADMIN'. |
| **Layer 3: 5-Attempt Brute-Force Lockout & Session Revocation** | **• Brute-Force Lockout:** The 'admin\_users\_2fa' table tracks 'failed\_attempts' and 'locked\_until'. Five failed password or 6-digit TOTP attempts within 15 minutes sets 'locked\_until \= NOW() \+ 15 minutes', blocks further login attempts from that account and IP, and logs 'ADMIN\_LOGIN\_LOCKOUT' in 'admin\_audit\_log'. **• Instant Session Kill:** When SUPER\_ADMIN suspends an admin or resets their 2FA on Screen 140, 'admin\_users\_2fa.session\_version' increments, immediately invalidating any active 4-hour cookie on their next click. |
| **Layer 4: Cryptographic & SQL Enforcement of User Privacy** | **• Zero Private Content in Admin Queries:** Admin API handlers for Users (127–128) and AI Operations (129–130) never run 'SELECT \*' on 'goals', 'tasks', 'evidence', or 'day\_notes'. They query SQL aggregate views (counts, storage bytes, timestamps, token counts) and return a static constant for content fields: 'CONTENT\_HIDDEN\_BY\_POLICY'. • Logged Exception for Public Abuse Reports Only (Screen 138): The '/api/admin/reports/\[id\]/inspect' endpoint only returns content if (a) a row exists in 'reports' with 'status \= OPEN', AND (b) the target goal/journey\_card has 'visibility \!= PRIVATE'. Fetching that endpoint executes inside a database transaction that inserts an immutable 'ABUSE\_REPORT\_CONTENT\_INSPECTED' record into 'admin\_audit\_log' before returning the response. |

**4\. File Storage Security, Quotas & Payment Anti-Spoofing**

Below is the exact verification flow for private file uploads (enforcing the 50 MB Free / 2 GB Pro quotas) and the anti-spoofing payment state machine.

| Security Flow | Step-by-Step Server & Database Enforcement |
| :---- | :---- |
| **Private Proof Upload Flow (Signed URLs \+ Quota Enforcement)** | **1\. Client Pre-Check & Compression:** Before uploading, the browser/PWA compresses photos to \~150–250 KB WebP/JPEG and checks video duration (\<= 30s) and file size (\<= 10 MB). **2\. Server Gate ('POST /api/tasks/:**id/evidence/upload-url'): The client sends '{ fileName, mimeType, fileSizeBytes, durationSeconds }'. The server verifies:    • The task belongs to 'auth.uid()'.    • Plan Type Check: If Free user and 'type IN (VIDEO, FILE)', reject (triggers Sheet 48). If Free user and 'type \= PHOTO' and user already uploaded 1 photo today across any goal, reject (triggers Sheet 47).    • Single-File Cap: 'fileSizeBytes \<= system\_settings.max\_file\_size\_bytes' (default 10 MB).    • Total Storage Quota: 'users.storage\_used\_bytes \+ fileSizeBytes \<= (isPro ? system\_settings.pro\_storage\_quota\_bytes : system\_settings.free\_storage\_quota\_bytes)' (default 2 GB Pro / 50 MB Free; triggers Sheet 119 if full). **3\. 60-Second Signed Upload URL:** If all checks pass, Supabase Storage issues a 60-second signed upload URL scoped to path 'users/{user\_id}/goals/{goal\_id}/{uuid}.{ext}' locking the exact 'content-length' and 'content-type'. **4\. Atomic Task Completion & Byte Accounting:** When the user taps 'Save proof and finish' (Screen 40), a single DB transaction inserts the 'evidence' row, marks 'tasks.status \= DONE', and increments 'users.storage\_used\_bytes'. When a proof, goal (Sheet 87), or account (Sheet 92\) is deleted, storage files are purged and 'storage\_used\_bytes' is decremented. |
| **Payment Webhook & Fake SMS Anti-Spoofing (UddoktaPay / SSLCommerz / bKash)** | 1\. Server-Created Checkout Only: 'POST /api/payments/checkout' reads the current active price for 'PASS\_1M \| PASS\_3M \| PASS\_6M \| PASS\_12M' directly from the database ('pricing\_plans')—never from client request body parameters—and creates a 'payments' row with 'status \= PENDING'. (Journey Cards are 100% free for all users; 'CERTIFICATE\_UNLOCK' is removed.) **2\. Zero Trust on Browser Redirects:** Landing on '/payment/success' (Screen 106\) only reads the database status; it never unlocks Pro. 3\. Three-Point Server Verification on Webhook ('POST /api/payments/webhook/:provider'):    • Check 1 (Cryptographic Signature): Verifies the 'RT-UDDOKTAPAY-API-KEY' / SSLCommerz HMAC signature header and logs the raw payload to 'payment\_events'.    • Check 2 (Server-to-Server Call Back): Calls the gateway's verification endpoint ('verifyPayment(invoice\_id)') directly from the Next.js server and verifies 'response.status \=== COMPLETED' and 'response.amount \=== payments.amount\_bdt'.    • Check 3 (Idempotent 'UNIQUE' Transaction): Runs 'SELECT \* FROM payments WHERE id \= \$1 FOR UPDATE'. Enforces a PostgreSQL 'UNIQUE' constraint on 'gateway\_transaction\_id'. If the transaction ID was already used, it flags 'DUPLICATE' and aborts. Otherwise, it sets 'payments.status \= COMPLETED' and sets 'users.pro\_until \= NOW() \+ pass\_duration' (since active Pro users cannot stack passes until expiry). |
